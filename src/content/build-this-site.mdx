This article is for developers who want to document an HTTP API they can call,
whether it's their own or one they use. You'll build a site like this one: an
introduction, a quickstart with code in three languages, a tutorial, a how-to
guide, a concepts page, a known-issues page, and an API reference whose
**Try it** button sends real requests.

The finished example is the site you're reading,
[past-dev-field-guide.vercel.app](https://past-dev-field-guide.vercel.app),
built from [github.com/reetbatra/past-dev-field-guide](https://github.com/reetbatra/past-dev-field-guide).
It documents [past.dev](https://past.dev), a memory API for AI agents. Every
example below comes from building it.

Before you start, you need:

- Node.js 22.18 or later, npm, Git, and the GitHub CLI (`gh`).
- A [Vercel](https://vercel.com) account and the Vercel CLI.
- An API key for the API you're documenting, and its OpenAPI file if it
  publishes one. past.dev's is at [past.dev/openapi.json](https://past.dev/openapi.json).
- Some familiarity with Markdown. Thally pages are MDX, which is Markdown plus
  components.

## Step 1: Create the project

[Thally](https://thally.io) is an open-source docs framework built on Next.js.
Its CLI creates a working site in one command.

### Scaffold the site

```bash
npx --yes create-thally-docs@latest past-dev-field-guide --yes --install
cd past-dev-field-guide
npm run dev
```

The command installs dependencies and makes the first Git commit. Open
[localhost:3040](http://localhost:3040) to see the starter site.

### Find the three files you'll edit

| Path | What it controls |
| --- | --- |
| `src/content/*.mdx` | The pages. Each needs `title` and `description` frontmatter. |
| `docs.json` | Navigation, logo, favicon, and the API reference source. |
| `src/data/site.ts` | The site name, description and header links. |

Leave the rest of `src/` and `starter-release.json` alone. Thally updates those
files with `npm run starter:update`, and your edits would conflict with it.

## Step 2: Keep your API key out of Git

You'll call the API many times while writing, so the key needs a safe home
before anything else.

### Know which env file is which

The scaffold creates two files that start with the same 133 lines:

- `.env.example` is committed to Git. It's a template for other people.
- `.env.local` is ignored by Git. Secrets go here.

They look identical in an editor. My key ended up in `.env.example`, and I only
caught it in `git diff` before committing.

### Add the key without it touching your screen

```bash
read -s "k?API key: " && echo "PAST_API_KEY=$k" >> .env.local && unset k
```

`read -s` hides what you paste and keeps it out of your shell history. This is
zsh syntax, the macOS default. In bash, use `read -s -p "API key: " k`.

### Check before every commit

```bash
git diff --cached | grep -E 'past_sk_' && echo "STOP: key staged"
```

Swap `past_sk_` for your API's key prefix. No output means nothing secret is
staged.

## Step 3: Replace the starter with your structure

The starter has eight placeholder pages and a sample API. You'll replace them
with pages that each do one job.

### Pick a content type for every page

GitHub's [content model](https://docs.github.com/en/contributing/style-guide-and-content-model/about-the-content-model)
and Mintlify's [content types guide](https://www.mintlify.com/docs/guides/content-types)
agree on four kinds of page. Decide which kind each page is before you write
it:

| Page on this site | Type | Its one job |
| --- | --- | --- |
| [Quickstart](/quickstart) | Quickstart | A first result in about 5 minutes and under 600 words |
| [Track facts that change](/tutorials/track-facts-that-change) | Tutorial | One complete, real workflow from start to finish |
| [Scope memory per customer](/guides/scope-memory-per-customer) | How-to | One task, named in the title |
| [How past.dev decides what's true](/concepts/how-memory-works) | Explanation | Why it works the way it does, with no steps |
| [Known issues](/known-issues) | Reference | Surprising behavior, what it breaks, what to do |

A page that tries to do two of these jobs gets long and hard to follow. My
first quickstart taught the API and explained its model at the same time. It
ran to 1,153 words, about twice GitHub's limit, until I split it into the
quickstart and the tutorial.

### Delete the starter pages

```bash
git rm src/content/components.mdx src/content/customization.mdx \
  src/content/guides/*.mdx src/content/api/authentication.mdx openapi.yaml
```

### Set the site's identity

In `src/data/site.ts`, replace the `siteConfig` values and keep the generated
`brand` fields:

```ts
export const siteConfig: SiteConfig = {
  name: 'past.dev field guide',
  description:
    'An unofficial, example-first guide to the past.dev memory API: send dated facts, recall what is true now, and scope memory per customer.',
  repoUrl: 'https://github.com/reetbatra/past-dev-field-guide',
  links: [
    { label: 'Official past.dev docs', href: 'https://past.dev/docs/memory-api/overview' },
  ],
  brand: brandPresets[brandPreset],
  brandPreset,
  brandPresets,
}
```

If you're documenting someone else's product, say so on the first page and
link to their official docs. Don't use their logo.

### Lay out the navigation by type

In `docs.json`, group the pages by the types you picked. Each string in `pages`
is a path under `src/content/` without `.mdx`:

```json
"tabs": [
  {
    "tab": "Get started",
    "groups": [
      { "group": "Get started", "pages": ["introduction", "quickstart"] },
      { "group": "Concepts", "pages": ["concepts/how-memory-works"] },
      { "group": "Tutorials", "pages": ["tutorials/track-facts-that-change"] },
      { "group": "How-to guides", "pages": ["guides/scope-memory-per-customer"] },
      { "group": "Reference", "pages": ["known-issues"] }
    ]
  },
  {
    "tab": "API Reference",
    "groups": [{ "group": "Overview", "pages": ["api/introduction"] }],
    "api": { "source": "openapi.json" }
  },
  { "tab": "Changelog", "href": "/changelog" }
]
```

The complete file is
[docs.json in the repo](https://github.com/reetbatra/past-dev-field-guide/blob/main/docs.json).

## Step 4: Run every request before you write about it

Write each page from requests you've actually sent, and paste the real
responses. A reader who runs your example and gets different output stops
trusting the rest of the page.

### Keep a helper that reads the key for you

This script reads the key from `.env.local`, so it never appears in a command
you type:

```bash
#!/usr/bin/env bash
# call.sh: call the API with the key from .env.local. Usage: ./call.sh GET /usage
set -euo pipefail
KEY=$(grep '^PAST_API_KEY=' .env.local | cut -d= -f2-)
curl -sS -X "$1" "https://api.past.dev/api/v1$2" \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  ${3:+-d "$3"} -w '\nHTTP %{http_code}\n'
```

Add `call.sh` to `.gitignore` if it lives inside the repo.

### Write down what surprised you

Running the API turned up four things I wouldn't have guessed. Each changed a
page:

- Processing took from 20 seconds to 8 minutes. So every script waits for
  `completed` before it asks a question.
- A field named `audiance` was accepted without an error. That became a
  warning in the how-to guide and an entry in [known issues](/known-issues).
- An invalid timestamp returned a `400` with no body at all. That went in the
  troubleshooting table.
- The same notes gave different extracted facts on different runs. So every
  page says "something like this" above its output.

### Run the page, not your notes

After writing a page, run its commands again exactly as printed, then replace
the output with what came back. This caught sample output in the how-to guide
that I had trimmed by hand, so it no longer matched what the command prints.

For code in several languages, save each version as a file, run all of them,
and paste them into the page from the files. This site's quickstart scripts
print identical output in curl, TypeScript and Python.

## Step 5: Write the pages

Thally pages are MDX with built-in components. This site uses:

- `<Steps>` and `<Step title="...">` for numbered procedures.
- `<CodeGroup>` for the same code in several languages. The word after the
  language becomes the menu label, as in `` ```typescript TypeScript ``. Use
  the same labels in every group on a page, and a reader's choice carries
  across all of them.
- `<AgentPrompt title="...">` for a prompt readers can copy into a coding
  agent. The quickstart has one.
- `<Note type="warning" title="...">` for anything that can lose data or
  leak it.
- `<Card>` and `<CardGroup cols="2">` for next steps.

Keep sentences under 25 words and paragraphs to two to four sentences, as
Mintlify's [style guide](https://www.mintlify.com/docs/guides/style-and-tone)
recommends. End every quickstart and tutorial with two or three next steps.

### Check as you go

```bash
npm run check -- --ci
```

A broken link fails the check. A broken `#anchor`, a missing description, or a
page left out of `docs.json` comes back as a warning. It caught three anchor
links on this site. Thally turns any run of punctuation in a heading into one
hyphen, so `past.dev` becomes `past-dev` and `doesn't` becomes `doesn-t`.

## Step 6: Generate the API reference

`"api": { "source": "openapi.json" }` turns every operation in the file into a
page with a **Try it** panel. Requests go through a relay on your docs server,
so the API doesn't need to allow your domain.

### Keep only the endpoints your guide covers

past.dev's spec has 34 operations, including account management this guide
doesn't cover. [`scripts/sync-past-openapi.ts`](https://github.com/reetbatra/past-dev-field-guide/blob/main/scripts/sync-past-openapi.ts)
downloads the spec and keeps 16 operations unchanged. It also fails if past.dev
removes one of them, so the reference can't quietly keep a dead endpoint.

```bash
npm run openapi:sync
```

```text
openapi.json: 16 operations from https://past.dev/openapi.json (version 1.0.0)
```

### Order the sidebar the way people use the API

By default, Thally groups endpoints by the spec's tags, in alphabetical order.
past.dev's tags put audiences first and recall last. Set `api.groups` in
`docs.json` to choose the order. Each page entry is an operation key:

```json
"api": {
  "source": "openapi.json",
  "groups": [
    {
      "group": "Send memory",
      "pages": ["POST /api/v1/ingest", "POST /api/v1/ingest/batch", "GET /api/v1/ingest/{ingestionId}", "DELETE /api/v1/ingest/{ingestionId}"]
    },
    { "group": "Recall", "pages": ["POST /api/v1/recall"] }
  ]
}
```

## Step 7: Brand the site

Put the logo and favicon in `public/`, and point to them from `docs.json`:

```json
"navbar": {
  "primary": { "label": "Quickstart", "href": "/quickstart" },
  "logo": {
    "light": "/brand/field-guide-logo-light.svg",
    "dark": "/brand/field-guide-logo-dark.svg",
    "showTitle": false
  }
},
"favicon": {
  "light": "/brand/field-guide-mark.svg",
  "dark": "/brand/field-guide-mark.svg"
}
```

Make the logo 28 pixels high and no more than 160 wide. Thally shrinks wider
logos to fit, and my first one, at 196 pixels, came out unreadable.

## Step 8: Publish on Vercel

### Build locally first

```bash
npm run typecheck
npm run build
```

If both pass here, the build passes on Vercel.

### Push and deploy

```bash
gh repo create past-dev-field-guide --public --source . --push
vercel link --yes --project past-dev-field-guide
vercel --prod --yes
```

`vercel link` connects the GitHub repo, so every later push to `main` deploys
on its own. The site needs no environment variables. Don't add your API key to
Vercel: the site never calls the API itself, and readers' **Try it** requests
carry their own keys.

`vercel link` also writes a `VERCEL_OIDC_TOKEN` line into `.env.local`. It
leaves your other lines alone.

## Troubleshooting

- **The header shows your name with a capital letter you didn't type.** Thally
  capitalizes the first letter of every site name, so "past.dev" showed as
  "Past.dev". Use a wordmark logo with `showTitle: false`, as in step 7.
- **You can't find where the logo goes.** It's `navbar.logo` in `docs.json`,
  documented in Thally's [branding guide](https://docs.thally.io/guides/branding-and-theming).
  Neither starter file mentions it.
- **Try it shows several identical "Authorization" fields.** The spec lists more
  than one way to authenticate, and Thally shows one field per method. Tell
  readers which one to fill, as this site's [API overview](/api/introduction) does.
- **The local site doesn't change after a rebuild.** An old `npm run start` may
  still hold port 3040, so the new one fails to start. Run
  `kill $(lsof -ti tcp:3040)`, then start again.

## Conclusion

You built a docs site for a real API: a quickstart in three languages, a
tutorial, a how-to guide, a concepts page, a known-issues page, and a reference
generated from the API's own spec. Every response on it came from a real
request, the same way the past.dev field guide was built.

## Next steps

- Write your quickstart around the API's most surprising behavior, not its
  first endpoint. For past.dev, that's knowing when a fact changed.
- Run your test scripts on a schedule in CI, so you hear about an API change
  before a reader does.
- Read GitHub's [templates](https://docs.github.com/en/contributing/writing-for-github-docs/templates)
  for the quickstart and tutorial page structures this site follows.
